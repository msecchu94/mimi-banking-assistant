# Chat API Contract

## 1. Overview

This document defines the V1 HTTP contract between the Flutter application
and the FastAPI backend for Mimi's conversational interface.

The contract allows Flutter to:

- send free-text messages;
- send structured user interactions;
- maintain a Conversation across requests;
- render backend-defined semantic UI responses;
- handle API failures through consistent HTTP semantics.

Flutter renders the response but does not own banking or conversational
business logic.

The backend remains authoritative for:

- intent interpretation;
- conversational state;
- financial data;
- financial validation;
- pending operations;
- operation execution;
- confirmation requirements.

The core principle remains:

> AI understands. Backend validates and executes.

---

## 2. Chat Endpoint

The V1 conversational contract uses one conceptual endpoint:

```http
POST /chat
```

The endpoint accepts either:

- a free-text user message; or
- a structured interaction generated by the UI.

It returns either:

```text
2xx → ChatResponse
4xx → ApiErrorResponse
5xx → ApiErrorResponse
```

Successful responses and error responses are separate contracts.

Errors must never be encoded as successful `200 OK` responses.

### Starting a Conversation

A Conversation is started before chatting:

```http
POST /conversations
```

The request has no body. It returns `201 Created`:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "conversation_state": "READY",
  "metadata": {
    "request_id": "req-50dc23a1",
    "timestamp": "2026-10-09T16:30:00Z"
  }
}
```

V1 serves a single configured demo customer and has no authentication; no
customer identity is sent by the client.

---

## 3. Chat Request

Conceptually:

```text
ChatRequest
├── conversation_id: UUID
├── message: string?
├── interaction: InteractionType?
└── payload: InteractionPayload?
```

### 3.1 Conversation ID

`conversation_id` identifies the active Conversation to which the interaction
belongs.

Example:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "message": "What's my balance?"
}
```

A request referencing a nonexistent or unavailable Conversation is an API
error.

---

## 4. Message and Interaction Exclusivity

A request must contain exactly one of:

```text
message
interaction
```

Conceptually:

```text
message XOR interaction
```

Valid:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "message": "Transfer 25,000 to Laura."
}
```

Valid:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "interaction": "CONFIRM",
  "payload": {
    "operation_id": "5b0c7d2e-3f41-4a6b-9c8d-1e2f3a4b5c6d"
  }
}
```

Invalid:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "message": "Yes.",
  "interaction": "CONFIRM",
  "payload": {
    "operation_id": "5b0c7d2e-3f41-4a6b-9c8d-1e2f3a4b5c6d"
  }
}
```

This prevents multiple sources of user intent within the same request.

---

## 5. Free-Text Messages

`message` contains natural-language input from the user.

Example:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "message": "What did I spend the most on this month?"
}
```

An empty or whitespace-only `message` is an invalid request.

Free-text messages may require LLM interpretation.

The backend is responsible for determining:

- intent;
- candidate entities;
- conversational references;
- whether deterministic financial processing is required.

Flutter does not interpret the banking meaning of the message.

---

## 6. Structured Interactions

Structured interactions represent deterministic UI actions.

Initial V1 interaction types are:

```text
InteractionType
├── CONFIRM
├── CANCEL
└── SELECT_CARD
```

Structured interactions should not be converted back into natural-language
messages by Flutter.

For example, pressing a confirmation button sends:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "interaction": "CONFIRM",
  "payload": {
    "operation_id": "5b0c7d2e-3f41-4a6b-9c8d-1e2f3a4b5c6d"
  }
}
```

rather than:

```json
{
  "message": "Yes."
}
```

This allows the backend to follow the deterministic path defined by the
conversational state model.

---

## 7. Interaction Payload

`payload` is optional and is only used by interactions that require
structured data.

### CONFIRM

Payload:

```text
operation_id: UUID
```

`operation_id` is the one received in the `CONFIRMATION` UI being confirmed.
`CONFIRM` authorizes only the operation currently waiting for confirmation
under that `operation_id`. A correction gives the corrected operation a new
`operation_id`, so a `CONFIRM` naming an earlier one is rejected with
`INVALID_INTERACTION` and changes nothing.

Example:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "interaction": "CONFIRM",
  "payload": {
    "operation_id": "5b0c7d2e-3f41-4a6b-9c8d-1e2f3a4b5c6d"
  }
}
```

### CANCEL

Payload:

```text
none
```

`payload` is omitted or `null`; an object payload is invalid.

Example:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "interaction": "CANCEL"
}
```

### SELECT_CARD

Payload:

```text
card_id: UUID
```

Example:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "interaction": "SELECT_CARD",
  "payload": {
    "card_id": "16e39f21-93b5-48b5-a8dc-90ad03ea5dd1"
  }
}
```

An interaction with an incompatible or malformed payload is an API error.

The payload structure is determined by the interaction type and must not be
treated as an unrestricted arbitrary object.

Unknown request or payload fields are invalid.

---

## 8. Chat Response

A successfully processed chat interaction returns a `ChatResponse`.

Conceptually:

```text
ChatResponse
├── conversation_id: UUID
├── message: string
├── intent: IntentType
├── conversation_state: ConversationFlowState
├── ui: UiResponse
└── metadata: ResponseMetadata
```

Example:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "message": "Your available balance is $120,000.",
  "intent": "GET_BALANCE",
  "conversation_state": "READY",
  "ui": {
    "type": "TEXT",
    "data": {}
  },
  "metadata": {
    "request_id": "req-50dc23a1",
    "timestamp": "2026-10-09T16:30:00Z"
  }
}
```

---

## 9. Intent

`intent` describes the backend's interpretation of the user request.

Initial V1 intents include:

```text
GET_BALANCE
GET_TRANSACTIONS
ANALYZE_EXPENSES
COMPARE_EXPENSES
GET_CARDS
FREEZE_CARD
UNFREEZE_CARD
GET_BENEFICIARIES
TRANSFER_MONEY
GENERAL_CONVERSATION
CANCEL
UNKNOWN
```

`intent` is informative from the client's perspective.

Flutter must not use `intent` to execute banking operations or reproduce
backend business logic.

For example, Flutter must not implement logic such as:

```text
if intent == FREEZE_CARD
    execute card freeze
```

Execution decisions belong to the backend.

---

## 10. Conversation State

`conversation_state` reflects the authoritative backend conversational flow
state defined by the conversational state model.

V1 values are:

```text
READY
COLLECTING_DATA
WAITING_CONFIRMATION
```

Flutter may use this information for presentation and observability, but it
must not reconstruct or independently advance the conversational state
machine.

The backend remains authoritative for state transitions.

---

## 11. UI Response

Each successful `ChatResponse` contains one primary semantic UI
representation:

```text
UiResponse
├── type: UiType
└── data: UiData
```

V1 supports:

```text
UiType
├── TEXT
├── CARD_LIST
├── CARD_SELECTOR
├── BENEFICIARY_LIST
├── CONFIRMATION
├── EXPENSE_SUMMARY
├── EXPENSE_COMPARISON
├── TRANSACTION_LIST
└── TRANSFER_SUMMARY
```

There is no `ERROR` UI type.

Errors use the separate `ApiErrorResponse` contract and appropriate HTTP
status codes.

The backend defines the semantic content.

Flutter defines visual presentation.

The backend must not send presentation-specific properties such as:

- colors;
- fonts;
- padding;
- widget classes;
- screen navigation instructions.

---

## 12. Typed UI Data

`ui.data` depends on `ui.type`.

Although represented as JSON, UI data is not conceptually an unrestricted
`Map<String, dynamic>`.

Each UI type has its own defined data shape.

Conceptually:

```text
TEXT                → TextUiData
CARD_LIST           → CardListUiData
CARD_SELECTOR       → CardSelectorUiData
BENEFICIARY_LIST    → BeneficiaryListUiData
CONFIRMATION        → ConfirmationUiData
EXPENSE_SUMMARY     → ExpenseSummaryUiData
EXPENSE_COMPARISON  → ExpenseComparisonUiData
TRANSACTION_LIST    → TransactionListUiData
TRANSFER_SUMMARY    → TransferSummaryUiData
```

This allows both FastAPI and Flutter to model the contract using typed
structures.

## 13. Text UI

`TEXT` represents a response that requires no additional structured visual
data.

Example:

```json
{
  "message": "Hello. How can I help you?",
  "intent": "GENERAL_CONVERSATION",
  "conversation_state": "READY",
  "ui": {
    "type": "TEXT",
    "data": {}
  }
}
```

`CARD_LIST` represents cards returned by a read-only card query.

Example:

```json
{
  "message": "You have two cards.",
  "intent": "GET_CARDS",
  "conversation_state": "READY",
  "ui": {
    "type": "CARD_LIST",
    "data": {
      "cards": [
        {
          "id": "16e39f21-93b5-48b5-a8dc-90ad03ea5dd1",
          "brand": "VISA",
          "type": "DEBIT",
          "last_four": "4821",
          "status": "ACTIVE"
        },
        {
          "id": "738b6767-11ef-45a9-8147-f67c9d37b411",
          "brand": "MASTERCARD",
          "type": "CREDIT",
          "last_four": "9314",
          "status": "ACTIVE"
        }
      ]
    }
  }

```

Flutter renders the cards but does not determine their financial state.

## 15. Card Selector UI

`CARD_SELECTOR` is used when the backend requires the user to select a card
to continue a pending operation.

Example:

```json
{
  "message": "Which card would you like to freeze?",
  "intent": "FREEZE_CARD",
  "conversation_state": "COLLECTING_DATA",
  "ui": {
    "type": "CARD_SELECTOR",
    "data": {
      "cards": [
        {
          "id": "16e39f21-93b5-48b5-a8dc-90ad03ea5dd1",
          "brand": "VISA",
          "type": "DEBIT",
          "last_four": "4821",
          "status": "ACTIVE"
        },
        {
          "id": "738b6767-11ef-45a9-8147-f67c9d37b411",
          "brand": "MASTERCARD",
          "type": "CREDIT",
          "last_four": "9314",
          "status": "ACTIVE"
        }
      ]
    }
  }
}
```

After selection, Flutter sends:

```json
{
  "conversation_id": "9e47b4c1-4a8c-4a3c-98d2-a31c9c87e641",
  "interaction": "SELECT_CARD",
  "payload": {
    "card_id": "16e39f21-93b5-48b5-a8dc-90ad03ea5dd1"
  }
}
```

Flutter does not need to know whether the selection belongs to a freeze or
unfreeze operation.

The backend resolves that meaning from the authoritative pending operation.

Example:

```json
{
  "message": "These are your saved beneficiaries.",
  "intent": "GET_BENEFICIARIES",
  "conversation_state": "READY",
  "ui": {
    "type": "BENEFICIARY_LIST",
```

## 17. Confirmation UI

`CONFIRMATION` represents a state-changing operation that is complete,
pre-validated, and waiting for explicit authorization.

Example:

```json
{
  "message": "Do you confirm transferring $25,000 to Laura?",
  "intent": "TRANSFER_MONEY",
  "conversation_state": "WAITING_CONFIRMATION",
  "ui": {
    "type": "CONFIRMATION",
    "data": {
      "operation_id": "5b0c7d2e-3f41-4a6b-9c8d-1e2f3a4b5c6d",
      "title": "Confirm transfer",
      "summary": {
        "type": "TRANSFER",
        "amount": {
          "amount": "25000.00",
          "currency": "ARS"
        },
        "beneficiary": "Laura"
      },
      "actions": [
        {
          "type": "CONFIRM",
          "label": "Confirm"
        },
        {
          "type": "CANCEL",
          "label": "Cancel"
        }
      ]
    }
  }
}
```

`summary.type` defines the summary's shape:

```text
TRANSFER → amount: Money, beneficiary: string
CARD     → card: the card, as in CARD_LIST
```

A card freeze or unfreeze summary:

```json
{
  "type": "CARD",
  "card": {
    "id": "16e39f21-93b5-48b5-a8dc-90ad03ea5dd1",
    "brand": "VISA",
    "type": "DEBIT",
    "last_four": "4821",
    "status": "ACTIVE"
  }
}
```

Flutter renders the available actions.

The actions do not authorize execution locally.

Selecting `CONFIRM` produces a new structured request to the backend carrying
this `operation_id`.

## 18. Expense Summary UI

`EXPENSE_SUMMARY` represents backend-calculated spending information for one
period.

Expenses are reported per currency. Currencies are never combined or
converted: `currencies` has one entry per currency with expenses, and is
empty when there were none. `to` is the last day of the period, inclusive.

Example:

```json
{
  "message": "You spent $185,000 this month. Dining was your largest category.",
  "intent": "ANALYZE_EXPENSES",
  "conversation_state": "READY",
  "ui": {
    "type": "EXPENSE_SUMMARY",
    "data": {
      "period": {
        "from": "2026-10-01",
        "to": "2026-10-31"
      },
      "currencies": [
        {
          "total": {
            "amount": "185000.00",
            "currency": "ARS"
          },
          "categories": [
            {
              "category": "DINING",
              "amount": {
                "amount": "85000.00",
                "currency": "ARS"
              }
            },
            {
              "category": "GROCERIES",
              "amount": {
                "amount": "60000.00",
                "currency": "ARS"
              }
            }
          ]
        }
      ]
    }
  }
}
```

Financial totals are calculated by the backend.

Flutter may visualize the supplied data but must not independently establish
financial truth.

## 19. Expense Comparison UI

`EXPENSE_COMPARISON` represents a backend-calculated comparison between two
periods.

Each currency is compared independently; currencies are never combined or
converted. A currency without expenses in one period counts as zero there.
`difference` is the non-negative magnitude of current minus previous, and
`change` carries its direction: `INCREASE`, `DECREASE` or `UNCHANGED`.
Flutter must not infer the direction from amounts.

Example:

```json
{
  "message": "You spent $25,000 more this month than last month.",
  "intent": "COMPARE_EXPENSES",
  "conversation_state": "READY",
  "ui": {
    "type": "EXPENSE_COMPARISON",
    "data": {
      "current_period": {
        "from": "2026-10-01",
        "to": "2026-10-31"
      },
      "previous_period": {
        "from": "2026-09-01",
        "to": "2026-09-30"
      },
      "currencies": [
        {
          "current_total": {
            "amount": "185000.00",
            "currency": "ARS"
          },
          "previous_total": {
            "amount": "160000.00",
            "currency": "ARS"
          },
          "difference": {
            "amount": "25000.00",
            "currency": "ARS"
          },
          "change": "INCREASE"
        }
      ]
    }
  }
}
```

The comparison and difference originate from backend financial processing.

## 22. Money Representation

Financial values use the domain `Money` representation:

```text
Money
├── amount: Decimal
└── currency: Currency
```

JSON represents the decimal amount as a string with exactly two decimal
places:

```json
{
  "amount": "25000.00",
  "currency": "ARS"
}
```

Financial amounts must not be transported as binary floating-point values.
An amount with more than two decimal places is never rounded; the backend
rejects it.

---

## 23. Response Metadata

V1 response metadata is intentionally minimal.

Conceptually:

```text
ResponseMetadata
├── request_id: string
└── timestamp: datetime
```

Example:

```json
{
  "request_id": "req-50dc23a1",
  "timestamp": "2026-10-09T16:30:00Z"
}
```

`request_id` allows a request to be correlated with backend logs and
diagnostics.

LLM-specific implementation information such as model name, prompt,
temperature, token usage, or confidence is not part of the Flutter API
contract.

---

## 24. API Error Contract

Failed API operations return an `ApiErrorResponse`.

Conceptually:

```text
ApiErrorResponse
├── code: string
├── message: string
├── request_id: string
└── timestamp: datetime
```

Example:

```http
404 Not Found
```

```json
{
  "code": "CONVERSATION_NOT_FOUND",
  "message": "The requested conversation was not found.",
  "request_id": "req-91af23c1",
  "timestamp": "2026-10-09T16:31:04Z"
}
```

Error codes are stable machine-readable identifiers.

`message` is a safe human-readable description.

Clients must not parse `message` to determine the error type.

Internal exception names, stack traces, SQL errors, infrastructure details,
or other sensitive diagnostic information must never be exposed through this
contract.

---

## 25. HTTP Error Semantics

The API uses HTTP status codes according to the nature of the failure.

Initial V1 policy:

| HTTP status | Meaning |
|---|---|
| `400 Bad Request` | Structurally invalid or unsupported request |
| `404 Not Found` | Requested resource does not exist |
| `409 Conflict` | Request conflicts with current resource or conversational state |
| `422 Unprocessable Entity` | Request is understood but violates validation or business rules |
| `500 Internal Server Error` | Unexpected backend failure |
| `503 Service Unavailable` | Required infrastructure or external dependency is temporarily unavailable |

Framework-level schema validation may also use `422 Unprocessable Entity`
according to the API framework's validation behavior.

The API must expose a consistent `ApiErrorResponse` shape for errors intended
for the Flutter client.

The following codes establish the initial V1 error vocabulary.

### Request and Conversation

### Financial Resources

```text
ACCOUNT_NOT_FOUND
```

```text
INSUFFICIENT_FUNDS

```

### Technical

```text
INTERNAL_ERROR

```

This list may be extended when implementation reveals a real V1 requirement.

New error codes must represent meaningful client-observable distinctions and
must not be created for internal implementation details.

## 27. Conversational Continuation Is Not an Error

A conversation requiring additional user input is a successful API
interaction.

Examples include:

- missing transfer amount;
- ambiguous card reference;
- waiting for confirmation;
- requesting clarification;
- asking the user to select a card.

These situations return:

```text
2xx
ChatResponse
```

with the appropriate:

```text
conversation_state
ui.type
ui.data
```

Example:

```text
COLLECTING_DATA + CARD_SELECTOR
```

is not an API failure.

By contrast, when a requested operation cannot be performed because of a
business, validation, resource, or state error, the API returns the
corresponding non-success HTTP response.

An operation that fails pre-validation or revalidation is discarded without
being executed, so no operation is pending afterwards. A state-changing
request made while another operation is pending returns
`409 PENDING_OPERATION_CONFLICT`; the pending operation is unchanged.

---

## 28. Error Mapping Boundary

The API contract defines:

```text
semantic error
        ↓
HTTP status
        +
ApiErrorResponse
```

The implementation mechanism used to produce that response is outside the
scope of this document.

Internal Application and Domain layers must remain independent from HTTP and
framework-specific error types.

Likewise, this contract does not prescribe how Flutter internally converts
HTTP failures into application failures or presentation state.

Those are implementation concerns on each side of the API boundary.

---

## 29. Request Correlation

Every response should expose a request identifier.

Conceptually:

```text
request
   ↓
request_id
   ├── backend logs
   ├── successful response metadata
   └── error response
```

For successful chat responses:

```json
{
  "metadata": {
    "request_id": "req-50dc23a1",
    "timestamp": "2026-10-09T16:30:00Z"
  }
}
```

For errors:

```json
{
  "code": "INTERNAL_ERROR",
  "message": "An unexpected error occurred.",
  "request_id": "req-50dc23a1",
  "timestamp": "2026-10-09T16:30:00Z"
}
```

This supports diagnostics without exposing internal implementation details.

---

## 30. Client Responsibility

Flutter is responsible for:

- sending valid `ChatRequest` objects;
- rendering the semantic `ui.type`;
- decoding the corresponding typed `ui.data`;
- sending structured interactions generated by UI controls;
- handling successful and failed HTTP responses according to this contract.

Flutter is not responsible for:

- determining banking intent;
- executing banking operations;
- validating financial rules;
- calculating authoritative financial totals;
- deciding whether confirmation is required;
- advancing the conversational state machine;
- interpreting pending operations;
- reconstructing backend business state.

---

## 31. Backend Responsibility

The backend is responsible for:

- interpreting free-text requests;
- processing structured interactions;
- maintaining authoritative conversational state;
- resolving domain references;
- validating financial operations;
- calculating financial results;
- requiring explicit confirmation;
- executing state-changing Use Cases;
- returning semantic UI data;
- returning appropriate HTTP errors when processing fails.

The backend must return enough structured information for Flutter to render the
result without reproducing banking logic.

---

## 32. Contract Invariants

The following invariants apply to the V1 Chat API:

1. A request contains exactly one of `message` or `interaction`.
2. `payload` is only valid when defined by the corresponding interaction.
3. Structured interactions remain structured and are not converted into
   artificial natural-language messages.
4. Successful chat processing returns a `ChatResponse`.
5. Failed processing returns an appropriate `4xx` or `5xx`
   `ApiErrorResponse`.
6. Errors are never encoded as successful `200 OK` responses.
7. `ApiErrorResponse.code` is machine-readable and stable.
8. Clients must not infer error type from human-readable messages.
9. One primary semantic UI representation is returned per successful
   `ChatResponse`.
10. `ui.data` has a defined structure for each `ui.type`.
11. Flutter renders semantic UI but does not execute banking logic.
12. `intent` does not authorize client-side business behavior.
13. `conversation_state` is authoritative from the backend.
14. Financial values are supplied by the backend.
15. Financial decimal values are transported without floating-point
    representation.
16. Internal backend errors and diagnostic details are never exposed to the
    client.
17. Conversational clarification and data collection are successful
    interactions, not API errors.
18. HTTP/framework concerns do not belong to Application or Domain contracts.

## 33. Scope of This Document

This document defines the V1 HTTP contract between Flutter and FastAPI.

It intentionally does not define:

- FastAPI router implementation;
- exception handler implementation;
- middleware implementation;
- Python exception hierarchy;
- repository implementation;
- Use Case implementation;
- LLM prompts or provider implementation;
- Dio interceptor implementation;
- Flutter repository implementation;
- Flutter failure hierarchy;
- `Either` implementation;
- Riverpod or BLoC state management;
- visual design;
- authentication;
- API versioning strategy;
- retry policies;
- idempotency implementation.

Those concerns belong to their corresponding backend, frontend, or
implementation decisions.
